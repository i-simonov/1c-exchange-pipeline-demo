Загрузка данных в библиотеке Конвейерного обмена данными: от входящего сообщения до проведенного заказа

В предыдущей статье мы выбирали объекты в 1С, запускали регистрацию к обмену и проверяли маршруты. Теперь пройдем входящий путь: возьмем сообщение с заказом, загрузим его вместе со складом и товарами, выполним отложенное проведение и посмотрим, что изменилось в базе. Затем загрузим обновление существующего заказа и исправим сообщение, которое завершилось ошибкой.

Пример построен на демонстрационном расширении Конвейерного обмена данными, на исходниках с версией демо-данных 5. В demo находятся рассматриваемые диспетчер загрузки, регистры очередей и прикладные обработчики. Отдельной установки ядра для повторения примера недостаточно.

Технические подробности вынесены в спойлеры «Как это устроено» под соответствующими шагами. Основную последовательность можно пройти через формы и один серверный вызов штатной обработки очереди. Ожидаемые результаты приведены для неизмененных демо-данных; статус проверки указан в конце статьи.

1. Подготавливаем пример: что уже есть в demo

Нужна отдельная тестовая база с указанной версией исходников demo. Проверьте, что константа Демо_КОД_ВерсияДанных имеет значение 5, а регламентные задания загрузки сообщений, повторной загрузки и отложенного процессинга отключены. В метаданных demo они отключены по умолчанию.

Откройте «Функции для технического специалиста → Регистры сведений» и найдите три списка:

  • «Входящая очередь сообщений (КОД)» — сообщения, ожидающие первичной загрузки;
  • «Ошибки загрузки сообщений (КОД)» — сохраненные сообщения, которые не удалось обработать штатным проходом;
  • «Отложенный процессинг (КОД)» — операции, которые предстоит выполнить над записанными объектами.

После начального заполнения эти списки содержат разные данные. Первую пачку demo уже попыталось загрузить: корректные данные записаны, неудачные сообщения сохранены в ошибках, для объектов созданы задания процессинга. Вторая пачка оставлена для самостоятельной работы. В ней 22 сообщения: 10 заказов, 6 товаров и 6 складов.

Для статьи понадобятся три сообщения второй пачки:

Значение demo_case в заголовках Назначение
pending-order-single Новый заказ IN3000101, один товар, количество 5
pending-order-update Обновление заказа IN3000004, новое количество 12
pending-order-invalid-date Заказ IN3000111 с неверным месяцем в дате

Ищите их по содержимому колонки «Заголовки». При необходимости установите отбор по вхождению значения demo_case. Номера сообщений и их идентификаторы не нужно копировать из чужой базы: они формируются при заполнении.

Если сообщения уже обработаны, обычный перезапуск базы не вернет их в очередь. Для повторения всей последовательности используйте свежую тестовую базу с теми же исходниками.

 
 Как это устроено: две пачки входящих сообщений

Модуль Демо_КОД_ОбновлениеИнформационнойБазы выполняет заполнение по версиям. Сначала создаются исходные объекты и сообщения версий 2 и 3. Генерация фиксируется, после чего запускается их загрузка. Затем добавляются сообщения версий 4 и 5, которые остаются во входящей очереди.

В заголовках сохраняются demo_version, demo_case и expected_result. Они помогают отличить учебные примеры и понять ожидаемый результат. После достижения версии данных 5 повторный запуск начального заполнения ничего не генерирует.

 

2. Разбираем входящее сообщение

Во входящей очереди найдите pending-order-single. Его отправитель — WEB, тип сообщения — order. Тело содержит номер и дату заказа, склад и массив строк items.

Ниже приведен фрагмент тела с полями, которые нужны для разбора:

{
  "number": "IN3000101",
  "date": "2026-09-02T12:00:00",
  "warehouse": {
    "guid": "bce02003-0001-4000-8000-000000000001",
    "code": "D3WH00001",
    "name": "Склад новых заказов"
  },
  "items": [
    {
      "line_number": 1,
      "product": {
        "guid": "bce02003-0003-4000-8000-000000000001",
        "code": "D3PR00001",
        "name": "Товар новых заказов"
      },
      "quantity": 5
    }
  ]
}

Отправитель и тип хранятся в полях записи очереди. Именно по ним выбирается сценарий. Значения внутри JSON описывают прикладные объекты, которые этот сценарий должен записать.

В полном демо-сообщении также есть поля guid и posted заказа. Текущий загрузчик ищет заказ по номеру и дате, а проведение оформляет отдельным заданием. Поэтому posted: true в теле не означает, что документ будет проведен непосредственно при загрузке.

 
 Как это устроено: от отправителя к сценарию

В переопределяемом модуле задана связь отправителя с обработкой-реестром:

РеестрыПоОтправителям["WEB"] =
    Метаданные.Обработки.Демо_КОД_РеестрСценариевЗагрузка_ОбменССайтом;

Диспетчер получает реестр, затем выбирает массив сценариев по типу сообщения:

РеестрСценариев = ПолучитьОбъектОбработки(РеестрМета)
    .РеестрКонвейеровРегистрации();
СценарииЗагрузки = РеестрСценариев[Сообщение.ТипСообщения];

Имя РеестрКонвейеровРегистрации() сохранено и у реестра загрузки: в текущем коде используется именно оно. Ключами этого реестра служат строки order, product и warehouse.

Для каждого сценария диспетчер собирает цепочку и создает контекст. В Контекст.Вход находятся исходное сообщение, прочитанный JSON и узел отправителя; в Контекст.Выполнение — сценарий и параметры запуска.

Связь отправителя с реестром и поиск узла обмена настраиваются отдельно. В demo строка WEB сопоставляется с узлом плана Демо_КОД_ОбменСайтом по коду. Если реестр или необходимый узел не найден, загрузка завершается ошибкой.

 

3. Загружаем заказ вместе со складом и товарами

Выберите строку pending-order-single и выполните «Загрузить сообщение». При успешном выполнении запись исчезнет из входящей очереди.

Откройте документ Демо_Заказ с номером IN3000101. Проверьте дату, склад и табличную часть: должна быть одна строка с товаром D3PR00001 и количеством 5.

Теперь откройте отложенный процессинг и найдите задание для этого заказа с видом обработки «Проведение». Загрузчики связанных справочников также ставят задания «Запись». Если такое задание для того же объекта уже было в очереди, новая загрузка обновляет его состояние.

Для нового заказа до выполнения процессинга ожидается следующая картина:

Что проверяем После загрузки
Документ и строка товара Записаны
Количество в строке 5
Общее количество заказа 0
Движения по регистру Демо_Заказы Отсутствуют
Задание проведения Находится в очереди

Сообщение уже обработано, а прикладная операция над заказом еще ожидает выполнения. Исчезновение записи из входящей очереди само по себе не подтверждает проведение документа.

 
 Как это устроено: загрузчик заказа и дочерние обработчики

Обработчик Демо_КОД_Обработчик_JSONВЗаказ ищет документ по точному совпадению номера и даты. Если документ найден, получает его объект; иначе создает новый. Затем устанавливает ОбменДанными.Загрузка = Истина и заполняет шапку.

Склад обрабатывается через Демо_КОД_Обработчик_JSONВСкладыХранения. Товары из items[].product собираются в массив и передаются загрузчику товаров:

Контекст.Выполнение.Вставить("ИзолированныйВызов", Истина);
СсылкиТоваров = ОбработчикТоваров.Обработать(Контекст, ДанныеТоваров);
ЗаполнитьТовары(Заказ, СтрокиЗаказа, СсылкиТоваров);

Дочерний обработчик возвращает ссылки в порядке входного массива. Повтор товара сохраняет свою позицию, а product: null дает пустую ссылку. По этим позициям заполняются строки заказа и количество из quantity.

Флаг ИзолированныйВызов относится к одному вызову: обработчик считывает и сбрасывает его при входе, возвращает собственный результат и не продолжает цепочку. Запись данных при этом выполняется обычным для загрузчика способом.

После подготовки связанных объектов заказ записывается вместе со своим заданием проведения в одной транзакции. Общей транзакции на все сообщение при первичной загрузке нет: склад или товар, успешно записанный до последующей ошибки, может остаться в базе.

 

4. Выполняем отложенное проведение

В списке «Отложенный процессинг (КОД)» выберите задание проведения заказа IN3000101 и нажмите «Обработать запись». Команда выполняет одну операцию для текущей строки списка.

После успеха задание удаляется. Повторно откройте заказ и проверьте «Общее количество»: теперь оно должно равняться 5. В регистре накопления «Заказы (регистр, Демо)», доступном в подразделе «Данные», отберите движения по этому заказу. Должна появиться одна строка со складом, товаром и количеством 5.

Проверка После загрузки После проведения
Количество в строке 5 5
Общее количество 0 5
Движения заказа Нет Одна строка с количеством 5
Задание проведения Есть Удалено

Аналогичный пример есть у справочников: обычная запись заполняет «Наименование для поиска» наименованием в верхнем регистре без пробелов по краям. Для нового загруженного элемента поле остается пустым до выполнения записи. У уже существовавшего элемента оно может сохранять прежнее значение до следующего процессинга.

 
 Как это устроено: загрузка и прикладная логика

В модуле заказа расчет итога расположен после проверки признака загрузки:

Если ОбменДанными.Загрузка Тогда
    Возврат;
КонецЕсли;

ОбщееКоличество = Товары.Итог("Количество");

Поэтому запись загрузчиком сохраняет полученные реквизиты и строки, а вычисление откладывается. Процессинг получает объект заново и выполняет обычное проведение. Обработчик проведения формирует по одному движению на каждую строку табличной части.

Задание определяется парой «Ссылка — Вид обработки». При ручном запуске оно блокируется и обрабатывается в транзакции. Успешная операция снимается с очереди, в том числе через подписки на события объекта.

Если ручное выполнение завершится ошибкой, изменения откатятся, исключение будет показано пользователю, а состояние задания и его счетчик останутся прежними. Регламентный процессинг при неудаче сохраняет новую ошибку и увеличивает счетчик попыток.

 

5. Загружаем обновление существующего заказа

В первой пачке начального заполнения есть заказ IN3000004. После ее загрузки он содержит одну строку с количеством 7,25. Сначала выполните его задание проведения и убедитесь, что общее количество и движение также равны 7,25.

Теперь во входящей очереди найдите pending-order-update и загрузите его командой «Загрузить сообщение». В теле переданы те же номер и дата, поэтому загрузчик должен обновить существующий документ. В его табличной части останется одна строка с количеством 12.

До нового процессинга общее количество и прежнее движение сохраняют значение 7,25. В очереди снова появляется задание проведения. Выполните его и проверьте результат:

Состояние заказа Количество в строке Общее количество Количество в движении
До обновления, после первого проведения 7,25 7,25 7,25
После загрузки обновления 12 7,25 7,25
После повторного проведения 12 12 12

При повторном проведении набор движений формируется заново. Для этого примера должна остаться одна строка с количеством 12.

 
 Как это устроено: замена состава и сопоставление объектов

Загрузчик полностью очищает табличную часть перед заполнением из items. Пустой массив очищает состав заказа, а warehouse: null очищает склад. Порядок строк определяется порядком массива; отдельной сортировки по line_number нет.

Справочники товаров, категорий и складов сопоставляются по GUID, который используется как идентификатор ссылки 1С. У заказа правило другое: точное совпадение номера и даты. GUID заказа из JSON в этом поиске не участвует.

Эти правила определяют поведение конкретного demo. Для своего обмена нужно отдельно выбрать устойчивый ключ сопоставления. Совпадение номера и даты само по себе не обеспечивает защиту от всех случаев повторной или параллельной доставки.

 

6. Разбираем ошибку загрузки

Найдите во входящей очереди pending-order-invalid-date. В его теле указан заказ IN3000111, а значение даты содержит месяц 13:

"date": "2026-13-01T12:00:00"

Выполните «Загрузить сообщение». Загрузчик должен сообщить о неверном формате даты. Запись при этом останется во входящей очереди: ручная команда вызывает диспетчер с пробросом исключения и не переносит сообщение в регистр ошибок.

Теперь выполним штатную обработку оставшейся очереди. Из серверной команды тестовой обработки или консоли кода, вне транзакции, вызовите:

КОД_ДиспетчерЗагрузкиСообщений.ПрочитатьВходящуюОчередьСообщений();

Вызов обрабатывает доступную входящую очередь порциями. Он затронет и остальные сообщения второй пачки. Отдельной команды массовой загрузки в рассматриваемой форме входящей очереди нет.

В штатном режиме ошибка отдельного загрузчика сохраняется вместе с сообщением в регистре ошибок, исходная запись удаляется, и обработка продолжается. Найдите пример в «Ошибках загрузки сообщений (КОД)». При выборе записи форма показывает сохраненное тело и подробное представление ошибки.

Способ запуска Что происходит при ошибке загрузчика
«Загрузить сообщение» во входящей очереди Ошибка передается пользователю, сообщение остается во входящей очереди
Штатный вызов диспетчера без параметров Сообщение сохраняется в ошибках и удаляется из входящей очереди
 
 Как это устроено: на каком этапе возникает ошибка

Сообщение может остановиться еще до записи объекта. Поврежденный JSON не позволит создать контекст, неизвестный отправитель — выбрать реестр или определить узел, неподдерживаемый тип — найти сценарий. Проверки даты и идентификаторов выполняются в прикладных загрузчиках.

В demo предусмотрен обработчик Демо_КОД_Обработчик_ВалидацияПоJSONSchema. В текущем реестре его подключение закомментировано. Пример с неверной датой обнаруживается загрузчиком и при отключенной проверке схемы.

Если включить JSON Schema первым этапом сценария, понадобится доступная внешняя компонента из поставки demo и настроенные схемы. Не следует ожидать, что все нарушения схемы будут отклоняться и без этого этапа: у загрузчиков свой набор проверок.

При записи ошибки сохраняются номер и идентификатор сообщения, отправитель, тип, заголовки, тело и подробная ошибка. Узел обмена сохраняется, если его удалось определить. Это позволяет повторно выполнить загрузку после исправления данных или настроек.

 

7. Исправляем сообщение и повторяем загрузку

В регистре ошибок выберите запись с заказом IN3000111. В поле «Сообщение» замените неверную дату на корректную:

"date": "2026-09-02T12:00:00"

Дальше выполните действия в таком порядке:

  1. Нажмите «Сохранить измененное сообщение».
  2. Оставьте выделенной только исправленную запись.
  3. Нажмите «Загрузить выбранные сообщения».
  4. Проверьте исчезновение записи ошибки и появление заказа IN3000111.
  5. Найдите его задание проведения и выполните «Обработать запись».

Сохранение — отдельный обязательный шаг. Повторная загрузка читает тело из регистра. Несохраненный текст редактора в нее не передается, а обновление формы может заменить его сохраненным значением.

Для одной успешно исправленной записи ожидается сообщение:

Загружено: 1. С ошибками: 0. Уже удалено: 0.

У этого демо-заказа пустой массив items. После проведения его общее количество должно остаться нулевым, а движений не будет. Успех проверяем по созданному документу, его проведению и снятию задания с очереди.

В форме есть еще две команды. «Взять на контроль» устанавливает признак контроля и ответственного для выбранных записей. Штатная повторная обработка такие записи пропускает. «Загрузить все сообщения» запускает обработку всего регистра ошибок независимо от отбора списка; записи на контроле и с исчерпанным лимитом попыток пропускаются.

Ручная команда «Загрузить выбранные сообщения» делает одну попытку для каждой выбранной записи, включая записи на контроле и записи с достигнутым лимитом. Поэтому для исправленного сообщения можно выполнить ручную попытку без сброса счетчика.

 
 Как это устроено: транзакция повторной загрузки

Модуль КОД_ПовторнаяЗагрузкаСообщений восстанавливает сообщение из регистра и снова выбирает сценарии по отправителю и типу. Используются те же загрузчики, что и при первичной обработке.

Вокруг повторной загрузки открывается транзакция: запись ошибки блокируется, выполняются все сценарии сообщения, затем запись ошибки удаляется. При успехе изменения фиксируются вместе. При неудаче прикладные изменения откатываются, а новый текст ошибки и счетчик сохраняются отдельной транзакцией.

По умолчанию массовый повтор допускает до пяти неудачных повторных попыток. Первичная ошибка создается с нулевым счетчиком. Массовый проход может сразу повторно выбрать неудачную запись, пока та не достигнет лимита: задержка между попытками в этом коде не задается.

Перед массовым повтором стоит устранить причину ошибки. Для исправления отдельного сообщения достаточно сохранить его тело и выполнить одну выбранную попытку.

 

8. Подключаем собственный сценарий загрузки

В разобранном примере диспетчер выбирает сценарий, конвейер организует вызовы, а загрузчик определяет правила записи прикладных объектов. Для нового типа сообщения понадобятся следующие настройки.

Связь отправителя с реестром. Она задается в КОД_ДиспетчерЗагрузкиСообщенийПереопределяемый.РеестрыСценариевПоОтправителям(). В ПриОпределенииУзлаОтправителя() настраивается соответствие транспортного отправителя узлу плана обмена.

Описание сценария. Реестр возвращает соответствие «тип сообщения → массив сценариев». В каждом сценарии указываются конвейер и упорядоченный массив обработчиков. В demo сценарий order содержит базовый конвейер загрузки и обработчик Демо_КОД_Обработчик_JSONВЗаказ; склад и товары он вызывает сам.

Прикладной загрузчик. Он определяет, как найти объект, какие реквизиты изменить, что означает пустой массив или null, какие проверки выполнить и какую операцию поставить в отложенную обработку.

Подключение процессинга. Если используются стандартные для demo операции записи или проведения, новый тип нужно включить в КОД_ОбъектыОтложеннойОбработки и проверить применимость подписок. Постановка задания должна выполняться в транзакции записи объекта.

 
 Как это устроено: контракт этапа и подмена реализации

Обработчики реализуют методы Следующий() и Обработать(Контекст, Вход = Неопределено). Конвейер связывает их в заданном порядке. Если явный вход не передан, прикладной загрузчик может взять данные из Контекст.Вход.ДанныеСообщения.

Экземпляры создаются через КОД_ДиспетчерЗагрузкиСообщений.ПолучитьОбъектОбработки(). Внутри вызывается переопределяемая процедура ПриПолученииОбъектаОбработки(): здесь можно подставить другую реализацию, сохранив контракт. Через эту фабрику обработчик заказа получает и дочерние загрузчики.

Границы транзакций задает реализация загрузки и вызывающий код. Само включение этапа в цепочку не делает несколько записей одной атомарной операцией.

 

Что учитывать в текущей реализации

  • Пример начинается с уже сохраненного сообщения. Прием по HTTP, чтение брокера и подтверждение внешней системе остаются задачами транспортного слоя. Исчезновение записи из входящей очереди описывает состояние обработки внутри demo.
  • Первичная и повторная загрузка имеют разные границы транзакций. В первичном пути каждый связанный объект сохраняется со своим заданием; общей транзакции сообщения нет. При повторе из регистра ошибок все сценарии сообщения и удаление ошибки охвачены общей транзакцией.
  • Новая загрузка снова ставит прикладную операцию в очередь. До ее выполнения вычисляемые поля и движения существующего объекта могут отражать прежние данные. Для нового заказа они еще не сформированы.
  • Счетчик и признак контроля относятся к конкретному механизму. Ручной повтор загрузки при ошибке обновляет запись ошибки и счетчик. Ручной процессинг объекта пробрасывает исключение без изменения задания. Эти режимы не следует считать одинаковыми.
  • Обновление объекта не означает однократную доставку. Текущий поиск заказа по номеру и дате и поиск справочников по GUID — прикладные правила сопоставления. Гарантии обработки повторов, параллельных потребителей и внешних подтверждений требуют отдельного решения.
  • Обратная регистрация учитывает контекст операции. Загрузчики передают отправителя и устанавливают запрет возврата ему через дополнительные свойства объекта. Отложенное проведение выполняется как самостоятельная локальная операция и не переносит эти свойства. Если для объекта подключен исходящий обмен, его результат нужно проверять с учетом этого различия.
