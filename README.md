# Демо конвейера обмена данными для 1С

Версия исходников: **2.0.0**.

`1c-exchange-pipeline-demo` — самостоятельное демонстрационное расширение 1С:Предприятия с готовым сценарием подготовки исходящих сообщений:

```text
Filter → Router → Исключение отправителя → Related registration → Mapper → Output
```

В расширение уже включено ядро [1c-exchange-pipeline](https://github.com/i-simonov/1c-exchange-pipeline), прикладные объекты, тестовые данные и четыре очереди ядра. Отдельно устанавливать расширение ядра не нужно.

> Demo изменяет данные и предназначено только для знакомства, разработки и тестирования. Не подключайте его к рабочей информационной базе.

## Что демонстрирует проект

- декларативные сценарии регистрации для заказов и товаров;
- фильтрацию новых и измененных данных с учетом предыдущей версии;
- маршрутизацию сообщений по складам и узлам плана обмена;
- преобразование заказов и товаров в JSON;
- сохранение сообщений во внутреннюю исходящую очередь;
- связанную регистрацию товаров из табличной части заказа;
- пакетный запуск и отдельный запуск этапов через отладочные формы.

## Требования

- платформа 1С:Предприятие 8.3.24 или новее;
- управляемое приложение;
- новая или отдельная тестовая информационная база;
- права на добавление расширений и запуск Конфигуратора.

БСП и внешние сервисы не требуются. Доставка сообщений из очереди во внешнюю систему намеренно не реализована.

## Быстрая установка из `.cfe`

### 1. Подготовьте тестовую базу

Создайте пустую файловую информационную базу либо используйте отдельную копию тестовой базы. Перед подключением к существующей базе сделайте резервную копию.

Если в базе уже установлено расширение ядра `КонвейерОбменаДанными`, удалите или отключите его: demo содержит собственную копию ядра, и одновременно устанавливать обе поставки не нужно.

### 2. Скачайте правильный файл

Откройте [опубликованный релиз demo](https://github.com/i-simonov/1c-exchange-pipeline-demo/releases/latest) и в блоке **Assets** скачайте расширение `.cfe` или архив исходников `.zip` нужной версии.

### 3. Подключите расширение

1. Запустите тестовую базу в режиме **Конфигуратор**.
2. Откройте **Конфигурация → Расширения конфигурации**.
3. Добавьте расширение из скачанного файла `.cfe`.
4. Подтвердите подключение и перезапуск сеанса, если платформа его запросит.
5. Убедитесь, что расширение `КонвейерОбменаДанными` активно и проверка применимости завершилась без ошибок.
6. Закройте Конфигуратор и запустите базу в режиме **1С:Предприятие**.

### 4. Дождитесь начального заполнения

При первом запуске расширение автоматически и в одной транзакции создает демо-данные. Повторный запуск не дублирует их: выполненная версия заполнения хранится в константе `Демо_КОД_ВерсияДанных`.

Откройте раздел **Конвейер обмена данными** и убедитесь, что доступны заказы, товары, склады, план обмена, обработчики и исходящая очередь.

Если раздел или данные не появились, проверьте активность расширения и события `Демо_КОД_НачальноеЗаполнение` в журнале регистрации.

## Какие данные появятся

После первого запуска будут созданы:

- категории «Электроника», «Бытовая техника» и «Инструменты»;
- склады «Основной склад», «Резервный склад» и «Региональный склад»;
- шесть товаров;
- текущий узел плана обмена `ERP`;
- внешние узлы `WEB`, `MARKET` и `B2B`;
- четыре заказа: три проведенных и один непроведенный.

Маршрутизация по умолчанию:

| Склад заказа | Получатели |
| --- | --- |
| Основной склад | `WEB`, `B2B` |
| Резервный склад | `MARKET` |
| Региональный склад | `B2B` |

Во время начального заполнения регистрация временно отключена, поэтому регистр **Исходящая очередь сообщений (КОД)** сначала будет пустым. Это ожидаемое поведение.

## Две пачки входящих сообщений

Первый запуск обновляет демо-данные до версии **5** и заполняет обе очереди:

1. Создает исходные справочники, узлы и заказы, если база новая (версия 1).
2. Добавляет прежние 16 примеров товаров, складов и заказа, если их еще не
   генерировали (версия 2), и еще **18 сообщений с заказами** (версия 3).
3. Фиксирует сообщения, затем запускает штатную загрузку демо-сообщений версий
   2 и 3. Корректные данные записываются, ошибки попадают в
   `КОД_ОшибкиЗагрузкиСообщений`, создаются задания отложенного процессинга.
4. Добавляет **22 сообщения**: 10 заказов (версия 4), 6 товаров и 6 складов
   (версия 5), включая ошибочные, и сохраняет версию 5. Эта пачка остается
   во входящей очереди для ручной или регламентной загрузки.

Дополнительные 18 сообщений первой пачки:

| Примеры | Результат |
| --- | --- |
| `order-single` | `IN3000001`: один товар, количество 3 |
| `order-mixed-items` | `IN3000002`: четыре строки, повтор товара, дробные количества и `product: null`, итог 4.75 |
| `order-empty` | `IN3000003`: пустой заказ без склада |
| `order-before-update`, `order-update` | `IN3000004`: смена склада и замена четырех строк одной, итог 7.25 |
| `order-before-clear`, `order-clear` | `IN3000005`: очистка склада и табличной части |
| `order-nested-category` | `IN3000006`: новый товар с вложенной категорией, количество 0.125 |
| `order-invalid-date`, `order-invalid-time` | Ошибки даты и времени заказа |
| `order-empty-warehouse-guid`, `order-empty-product-guid`, `order-empty-category-guid` | Ошибки нулевых GUID склада, товара и категории |
| `order-invalid-warehouse-guid`, `order-invalid-product-guid` | Ошибки формата GUID |
| `order-broken-json`, `order-unknown-sender` | Поврежденный JSON и неизвестный отправитель |
| `order-after-errors` | `IN3000007`: корректный заказ после ошибок, 25 строк, итог 81.25 |

Из этих 18 сообщений девять успешно загружаются, девять остаются в регистре
ошибок. Во второй пачке — 11 корректных и 11 ошибочных сообщений:

| Тип сообщения | Корректные | Ошибочные | Примеры |
| --- | ---: | ---: | --- |
| `order` | 5 | 5 | Новые заказы `IN3000101`–`IN3000104`, обновление `IN3000004` до количества 12; неверная дата, нулевые GUID и поврежденный JSON |
| `product` | 3 | 3 | Создание товара с категорией, обновление с очисткой категории, товар после ошибок; нулевые GUID товара и категории, поврежденный JSON |
| `warehouse` | 3 | 3 | Создание и обновление склада, склад после ошибок; нулевой и некорректный GUID, поврежденный JSON |

Товары и склады представлены отдельными сообщениями. Коды в заголовках начинаются
с `pending-order-`, `pending-product-` и `pending-warehouse-`. Корректные сообщения
справочников создают по два новых товара и склада (`D5PR00001`–`D5PR00002`,
`D5WH00001`–`D5WH00002`) и категорию `D5CAT0001`.

Заголовки сохраняют `demo_version`, `demo_case` и `expected_result`.
Отправитель корректных сообщений — WEB. Новые ошибочные сообщения отклоняются
и без JSON Schema: соответствующие проверки выполняют загрузчики и диспетчер.
В текущем реестре обработчик JSON Schema отключен. Старые примеры версии 2
с кодами `schema-*` проверяют именно схему; их результат зависит от ее включения.
Если включить проверку, должна быть доступна внешняя компонента JSON Schema.

Загрузка выполняется после фиксации генерации, вне ее транзакции. При прерывании
на версии 3 следующий запуск продолжит оставшиеся начальные сообщения и добавит
вторую пачку. На базе версии 4 обновление добавляет только 12 сообщений товаров
и складов, сохраняя существующие очереди. После достижения версии 5 перезапуск
не генерирует сообщения заново и не загружает вторую пачку.
Сообщения без демо-заголовков автоматическое начальное
заполнение не обрабатывает. На базе версии 2 обновление также выполняется один раз.

Откройте **Входящую очередь сообщений** для второй пачки и **Ошибки загрузки
сообщений** для результатов первой. Регламентные задания в поставке отключены;
если вы включили их в своей базе, они могут обработать вторую пачку и задания
процессинга сразу после заполнения.

## Разница между загрузкой и процессингом

У товаров, категорий и складов есть реквизит **Наименование для поиска**.
Обычная запись заполняет его наименованием в верхнем регистре без пробелов
по краям. У заказа реквизит **Общее количество** содержит сумму колонки
`Количество` табличной части. Оба вычисления выполняются в `ПередЗаписью`
после возврата при `ОбменДанными.Загрузка = Истина`.

При обычном проведении заказ записывает по одному движению на каждую строку
в оборотный регистр накопления `Демо_Заказы` — **Заказы (регистр, Демо)**.
Измерения — склад и товар, ресурс — количество, период — дата заказа.
Повторное проведение заменяет движения, в том числе при очистке табличной части;
отмена проведения удаляет их.

Чтобы увидеть разницу, приостановите регламентное задание процессинга,
загрузите корректные входящие сообщения и сравните данные до и после команды
**Обработать запись** в очереди процессинга:

| Объект | После первичной загрузки | После процессинга |
| --- | --- | --- |
| Товар, категория, склад | Наименование для поиска пустое | Заполнено из наименования |
| Заказ `IN0000001` | Общее количество 0, движений нет | Общее количество 4.5, три движения |

Регистр движений доступен в подразделе **Данные**. Вычисляемые реквизиты видны
в стандартных формах объектов. После повторной загрузки уже обработанного
объекта вычисляемые поля и движения сохраняют прежние значения до следующего
процессинга. Это позволяет увидеть, что прикладная обработка еще не выполнена.

На новой базе начальное заполнение записывает справочники и заказы обычным
способом, поэтому эти поля заполнены, а проведенные заказы имеют движения.
При обновлении существующей базы прежние объекты нужно записать или перепровести,
чтобы получить новые вычисляемые значения и движения. После демонстрации
возобновите регламентное задание процессинга.

## Ручной отложенный процессинг

Откройте регистр `КОД_ОтложенныйПроцессинг` через функции технического
специалиста, выберите строку и нажмите **Обработать запись**. Команда выполняет
одну операцию по паре `Ссылка` и `ВидОбработки`, даже если выделено несколько строк
или исчерпан лимит автоматических попыток. В списке видны объект, вид обработки,
состояние, номер попытки и текст ошибки.

При успехе задание удаляется, список обновляется. Действуют обычные подписки:
запись снимает задание записи, проведение — проведения, распроведение —
распроведения, установка пометки удаления — пометки. Другие операции остаются
в очереди; физическое удаление объекта снимает все его задания.
При ошибке платформа показывает исключение, изменения откатываются; задание,
его состояние, счетчик попыток и прежний текст ошибки сохраняются.
Если задание уже удалено, команда сообщает об этом и не выбирает другое.

Для вызова на сервере вне транзакции используйте
`КОД_ОтложенныйПроцессинг.ОбработатьЗадание(Ссылка, ВидОбработки)`.
Функция возвращает `Истина` при успехе и `Ложь`, если задания уже нет.
Ручной и регламентный запуск блокируют выбранное задание перед обработкой.

Подписки подключены ко всем документам и справочникам, но снимают задания
только для ссылок из `КОД_ОбъектыОтложеннойОбработки`: заказа, товаров, категорий
и складов. Состояние и число попыток не мешают снятию выполненной операции.
Удаление заданий входит в транзакцию объекта: отказ или откат сохраняет очередь.
Загрузчики ставят новое задание после записи объекта в той же транзакции.
В demo-заказе нет статуса «Закрыт»; прикладное условие отмены проведения
остается в `ДокументЗакрытДляОтложенногоПроведения` переопределяемого модуля.

## Загрузка склада и товаров заказа

Формат заказа сохраняет строки `items` с полями `line_number`, `product` и `quantity`.
`Демо_КОД_Обработчик_JSONВЗаказ` собирает `items[].product` в массив в исходном порядке
и передаёт его дочернему обработчику через тот же контекст:

```bsl
Контекст.Выполнение.Вставить("ИзолированныйВызов", Истина);
СсылкиТоваров = ОбработчикТоваров.Обработать(Контекст, ДанныеТоваров);
```

Экземпляр получается через `КОД_ДиспетчерЗагрузкиСообщений.ПолучитьОбъектОбработки`
и кэшируется внутри обработчика заказа. В `ПриПолученииОбъектаОбработки` его можно
заменить внешней обработкой с такой же функцией `Обработать(Контекст, Вход = Неопределено)`.
Обработчик считывает и сбрасывает одноразовый флаг при входе, возвращает результат
без продолжения цепочки и без добавления дочернего выхода в отладку.

Склад загружается перед товарами через `Демо_КОД_Обработчик_JSONВСкладыХранения`
по тому же механизму фабрики, кэша и изолированного вызова. Поле `warehouse`
передаётся массивом из одного объекта, возвращённая ссылка заполняет `Заказ.Склад`.
При `warehouse: null` склад заказа очищается без вызова дочернего обработчика.
Результат загрузчика складов проверяется: массив должен содержать ровно одну
ссылку типа `СправочникСсылка.Демо_КОД_СкладыХранения`.
Склад записывается вместе со своим заданием процессинга до записи заказа;
без внешней транзакции последующая ошибка товаров или заказа не отменяет склад.

Загрузчик товаров использует явно переданный `Вход`, включая пустой массив;
при `Неопределено` берёт `Контекст.Вход.ДанныеСообщения`.
Он возвращает массив ссылок той же длины и в том же порядке: повторяющиеся товары
сохраняют свои позиции, `product: null` даёт пустую ссылку.
Каждый товар и категория записываются в отдельной транзакции вместе со своим заданием
процессинга. Заказ открывает транзакцию только для собственной записи и задания проведения.
Без внешней транзакции ошибка следующего объекта не отменяет уже записанные объекты.

Заказ полностью перезаполняет табличную часть по `items`: порядок задаётся массивом,
количество берётся из `quantity`. Повторная загрузка заменяет прежний состав,
пустой массив очищает его. Несовпадение количества ссылок и строк вызывает ошибку
до записи заказа. Отдельные шаги `JSONВСкладыХранения` и `JSONВТовары` перед `JSONВЗаказ` не требуются.

## Первый запуск сценария

1. В разделе **Конвейер обмена данными** откройте список демо-заказов.
2. Выберите один из трех проведенных заказов.
3. Измените количество товара или другой реквизит.
4. Повторно проведите документ.
5. Откройте **Исходящая очередь сообщений (КОД)**.

В очереди должны появиться:

- сообщения типа `Документ.Демо_Заказ` для получателей, соответствующих складу заказа;
- сообщения типа `Справочник.Демо_КОД_Товары` для товаров из табличной части заказа и тех же направлений обмена.

Тело содержит актуальное JSON-представление объекта. В заголовках записываются тип операции и тип содержимого.

## Дополнительные проверки

### Фильтрация

Запишите непроведенный заказ — сообщений быть не должно. Проведите тот же заказ: он пройдет Filter и попадет в очередь.

### Изменение маршрута

У проведенного заказа смените основной склад на резервный и снова проведите документ. Сообщение должно быть подготовлено для нового получателя `MARKET`, а также для прежних `WEB` и `B2B`, которым могла быть известна предыдущая версия заказа.

### Пакетный запуск (драфт)

Обработка **Ручная регистрация (драфт)** не реализована полностью, но в ней размечен подход к функционалу, аналогичному БСП-форме "Состав отправляемых данных".

Ручной запуск выполняет очередь регистрации в пределах выбранного плана. Для исходного
типа объектов используются отмеченные конвейеры и обработчики; сценарии остальных типов
сохраняются в реестре для связанных заданий. Если включена связанная регистрация товаров,
сообщения заказов и их товаров подготавливаются за один запуск. Расшифровка формы по-прежнему
показывает только выбранные исходные объекты.

### Контекст и очередь регистрации

`НовыйКонтекстРегистрации(РеестрСценариев, МенеджерВременныхТаблиц = Неопределено,
РежимВыполнения = Неопределено)` требует готовый реестр первым аргументом.
`КонтекстРегистрации.РеестрСценариев` имеет структуру «план обмена → объект метаданных →
массив сценариев» и используется для всей очереди, включая задания из обработчиков.
Вызывающий код подготавливает реестр до создания контекста; реестр и вложенные сценарии
не следует изменять во время выполнения. Пустой реестр допустим и ничего не запускает.
При отсутствии сценариев для типа задания в плане этот план пропускается.

`ЗарегистрироватьПоРееструСценариев` сохраняет прежний интерфейс для подписок: перед
созданием контекста она получает все стандартные реестры один раз. Исполнитель очереди
не обращается к настройкам подключения реестров.

Для программного запуска с собственным составом сценариев:

```bsl
// Подключения: соответствие выбранных планов обработкам-реестрам.
Реестр = КОД_ДиспетчерРегистрацииКОбмену.ПолучитьРеестрСценариевРегистрации(Подключения);
// Здесь можно изменить состав сценариев и обработчиков для этой операции.
Контекст = КОД_ДиспетчерРегистрацииКОбмену.НовыйКонтекстРегистрации(Реестр);
КОД_ДиспетчерРегистрацииКОбмену.ДобавитьЗаданиеРегистрации(Контекст, ОбъектМетаданных, Ссылки);
Результаты = КОД_ДиспетчерРегистрацииКОбмену.ВыполнитьЗаданияРегистрации(Контекст, Истина);
```

Контекст предназначен для одного запуска. Второй аргумент `ВыполнитьЗаданияРегистрации`
включает сбор таблиц `Ссылка/Узел` по всем выполненным сценариям до очистки временных таблиц.
По умолчанию сбор отключен, результат — пустой массив; это не мешает выполнению заданий.
Сценарий без результата маршрутизации возвращает пустую таблицу из базового конвейера.
`ВТ_ПредыдущаяВерсия` сохраняется между сценариями.

При переходе со старого API необходимо обновить прямые вызовы `НовыйКонтекстРегистрации`:
менеджер временных таблиц теперь передается вторым аргументом. Вызовы
`ЗарегистрироватьПоРееструСценариев` и `ДобавитьЗаданиеРегистрации` не меняются.

### Отдельные этапы

Откройте формы Filter, Router или Mapper в группе демо-обработчиков. Формы подготавливают входной контракт этапа и позволяют исследовать его результат без полного автоматического сценария.

### Ручная загрузка JSON

У обработчиков `Демо_КОД_Обработчик_JSONВЗаказ`, `Демо_КОД_Обработчик_JSONВТовары`
и `Демо_КОД_Обработчик_JSONВСкладыХранения` есть одинаковые формы загрузки:

1. Выберите узел в поле **План обмена (узел)**. При первом открытии подставляется `WEB`.
2. Выберите **Сценарий** из реестра загрузки. Список содержит только сценарии
   выбранного плана с текущим обработчиком и учитывает ограничение по коду узла.
3. На вкладке **JSON сообщения** вставьте тело сообщения: объект заказа либо
   массив товаров или складов, как во входящей очереди. Заголовки отдельно вводить
   не требуется; тип сообщения и отправитель берутся из выбранного сценария.
4. Нажмите **Загрузить**. Форма откроет вкладку **Сообщение → объект** с исходными
   данными, ссылками, признаком ошибки и ее описанием. Для массива выводится строка
   на каждый элемент в исходном порядке, включая повторы и допустимый `null` товара.

Команда вызывает текущий обработчик в режиме отладки; следующий этап цепочки
не запускается. Объекты записываются, а проведение заказа и обработка справочников
остаются в очереди отложенного процессинга. Весь ручной запуск выполняется в одной
транзакции: при ошибке откатываются и дочерние объекты, и их задания. В результате
остается одна строка с исходным JSON и ошибкой, без ссылок на отмененные записи.
Ручная загрузка не добавляет и не удаляет сообщения во входящей очереди или регистре ошибок.

Узел, сценарий и JSON сохраняются в настройках формы; результаты каждого запуска
заменяют предыдущие. Подбор сценария, запуск и подготовка результата реализованы
в модуле каждой формы.

## Установка из исходников

1. Клонируйте репозиторий:

   ```bash
   git clone https://github.com/i-simonov/1c-exchange-pipeline-demo.git
   ```

2. Создайте тестовую информационную базу и откройте ее в Конфигураторе.
3. В окне **Расширения конфигурации** создайте пустое расширение.

## Обновление встроенного ядра

Этот раздел нужен разработчикам demo. Пользователю готового `.cfe` выполнять синхронизацию не требуется.

По умолчанию репозитории должны лежать рядом:

```text
parent/
├── 1c-exchange-pipeline/
└── 1c-exchange-pipeline-demo/
```

Обновите локальное ядро и запустите синхронизацию из demo:

```bash
git -C ../1c-exchange-pipeline pull --ff-only
./scripts/sync-core.sh
```

Другой путь можно передать аргументом:

```bash
./scripts/sync-core.sh /path/to/1c-exchange-pipeline
```

Скрипт:

- требует чистого рабочего дерева ядра;
- копирует только объекты из белого списка;
- точечно переносит их `configVersion` в `ConfigDumpInfo.xml`;
- записывает использованный commit ядра в `CORE_VERSION`;
- не заменяет `Configuration.xml`, прикладные объекты demo, общие модули с суффиксом `Переопределяемый` и состав типа `КОД_ОбъектыОтложеннойОбработки`;
- проверяет UUID вложенных метаданных регистров; отсутствие `configVersion` у измерений, ресурсов и реквизитов допустимо.

Белый список включает четыре очереди, их формы и команды, диспетчер загрузки, базовый конвейер загрузки, повторную загрузку, отложенный процессинг, его перечисления и подписки, константу порции, регламентные задания и Output-обработчик. Новые объекты и изменения структуры `Configuration.xml` сначала интегрируются вручную; скрипт проверяет согласованность готовой структуры.

В переопределяемых модулях demo сохраняются привязка `WEB`, его узел плана обмена и прикладные правила. В определяемом типе остаются заказ, товар, категория и склад. Имена перенесённых объектов больше не содержат `Демо_`; UUID сохранены. Полная граница core/demo описана в [руководстве ядра](https://github.com/i-simonov/1c-exchange-pipeline/blob/main/docs/loading.md).

После синхронизации проверьте diff, загрузите исходники в тестовую базу и повторите основной сценарий.

## Известные ограничения

- demo не отправляет сообщения во внешние системы;
- повторы загрузки и очередь ошибок реализованы; подтверждения внешней доставки и защита от повторной доставки подключаются отдельно;
- снимок предыдущей версии не включает табличные части;
- автоматическая подписка показана на документах;
- обработка ручной регистрации имеет статус draft;
- расширение создает собственные прикладные данные, поэтому предназначено только для тестовой базы.

## Возврат данных отправителю

В сценарии заказов и товаров после Router подключен `КОД_Обработчик_ИсключениеОтправителя`, перед связанной регистрацией и преобразованием в JSON. Явное решение записывающего загрузчика имеет приоритет над настройкой сценария; без решения используется `ОтправлятьОбратноОтправителю` сценария, по умолчанию `Ложь`.

JSON-загрузчики заказов, товаров, категорий и складов устанавливают дополнительные свойства `КОД_Отправитель` и `КОД_ОтправлятьОбратноОтправителю = Ложь`. Для передачи отправителя включать объект в состав плана обмена не требуется. Чтобы разрешить ответ с результатами обработки, установите это дополнительное свойство объекта в `Истина` перед записью. Существующие подписки регистрации демо подключены к заказам; установка свойств на справочниках сама по себе не добавляет подписок регистрации.

Первичная и повторная загрузка определяют узел через `КОД_ДиспетчерЗагрузкиСообщений.УзелОтправительСообщения`: сохраненный `УзелОбмена` имеет приоритет. Если его нет, переопределяемый модуль в демо ищет узел плана `Демо_КОД_ОбменСайтом` по строковому отправителю. Для другого транспорта измените эту прикладную точку соответствия. Неизвестный узел не допускает запись объекта; сообщение об ошибке сохраняет строкового отправителя для повторной попытки после настройки.

Отложенный процессинг остается самостоятельной локальной операцией и не переносит эти свойства. Поэтому последующее проведение может отправить результат исходному отправителю. Связанные задания используют уже отфильтрованные маршруты родителя, но не наследуют его отправителя автоматически.
